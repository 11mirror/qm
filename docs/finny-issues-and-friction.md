# Finny Issues & Friction Log

Date: 2026-11-17

## 1. Plan Skill Quality & Preflight SOP Decomposition

- **Problem**: The current preflight plan presentation generated by the LLM is generic and lacks concrete execution details and SOP decomposition.
- **Requirement**:
  - Integrate a dedicated planning skill or rigorous preflight SOP logic.
  - Decompose user intent into explicit accounting/engineering logic (systems, tables, fields, transaction flows).
  - Clarification loop: If gaps or ambiguities exist in the SOP/scope, present interactive question-answer clarification cards to the human before finalizing the plan and asking for approval.
  - Prevent jumping straight into execution with unclarified assumptions.

## 2. Duplicate Approval Confirmation Messages in UI

- **Problem**: When a user approves a Finny plan card in the Web UI, the confirmation message (`Finny plan "..." approved. Background Producer and Auditor workers have been dispatched...`) is rendered and appended twice in the chat transcript.
- **Root Cause**:
  - `orchestrator.ts` appends an `AgentMessage` directly to the session transcript via `deps.sessions.append(writer, { kind: "AgentMessage", text: reply })` and also returns `reply` in the turn outcome.
  - The Web UI streaming runner (`driveApproval` / `resumeRun`) receives the completion reply and appends or commits it as well, creating duplicate rows in the transcript.
- **Fix Needed**: Consolidate approval acknowledgment so the confirmation message is emitted exactly once across both the transcript store and UI stream handler.

## 3. Creation Scope vs. Owner Scope Binding Mismatch & Immutable Binding Friction

- **Problem**:
  - Inbound files uploaded via `/v1/files/upload` are tagged with `ownerScopeId: "personal:<actorId>"` while `createdInScope` is set to the project/organization scope (e.g. `org:sharechat` or a project group).
  - Finny verification and audit rules previously checked strict equality on `ownerScopeId === job.scopeId`, failing with:
    > _"Certification is currently blocked by a Core validation defect: it rejected the immutable file because its verified creation scope and owner scope differ."_
- **Re-architecture Needed**:
  - Rethink and simplify the rigid immutable file scope binding rules.
  - Files created within an approved project/org context should be natively valid for Finny audit and certification without requiring convoluted workarounds or fragile scope matching.
  - Clearly distinguish between artifact provenance/ownership and context eligibility.
